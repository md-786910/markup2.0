## Phase 1: Security audit (highest priority)

### 1A. Proxy and SSRF

#### S-01 · CRITICAL · The proxy is an anonymous open proxy, and it hands other sites' cookies to the attacker
This finding combines two problems that become critical together.

**1. Open proxy**
- **Where:** `server/controllers/proxy.controller.js:544-579`, `middleware/proxyAuth.js:208-211`, `app.js:108` (mounted before `globalLimiter` at `:124`).
- With `guest=true`, the only requirement is that `projectId` points at any project with sharing turned on.
- `url` is never compared with the project's `websiteUrl`.
- Every HTTP method is forwarded, with a raw body of up to 10 MB.
- There is no rate limit.
- **What an attacker does:** they sign up for a trial (no card needed), create a project and share it. They now have an unauthenticated, unlimited proxy that fetches any public URL from your server's IP. It can be used for scraping, credential stuffing or spam form posts. Their own HTML is served on `api.<your-domain>`, which risks your API domain landing on Safe Browsing or spam blocklists. That would break the product for every customer.

**2. Cookie forwarding**
- **Where:** `proxy.controller.js:649-661`.
- Every cookie on the API host, except `markup_*`, is forwarded to whatever URL is being proxied, along with the `Authorization` header.
- Site cookies are re-scoped to `Path=/` on the API host (`:387-393`), so all reviewed sites share one cookie jar.
- **Scenario:**
  1. An agency user signs in to client A's staging site through the proxy.
  2. The attacker sends them a link to `api…/api/proxy?url=https://evil.example/&projectId=<attacker's shared project>&guest=true`.
  3. evil.example receives client A's session cookies in the `Cookie` header, HttpOnly ones included.
  4. JavaScript on that page can also read the non-HttpOnly cookies, including the `__markup_ls_*` tokens mirrored from other sites' localStorage.

**Fix**
1. Allow proxied pages only on the project's registrable domain, plus an allowlist the project manager can edit. Allow assets from other hosts for GET only.
2. Add a per-IP and per-project limiter on `/api/proxy`.
3. Require a signed guest proxy token bound to the share token, not just a `projectId`. This also closes the known gap where the share password isn't checked.
4. Store site cookies namespaced per site (for example `__mk_c_<siteKey>__name`) and forward only the target site's cookies.
5. Structural fix: serve the proxy from a separate sandbox domain.

#### S-02 · MEDIUM · Mirrored localStorage tokens cross between customers on shared hosting
- **Where:** `utils/proxyRewriter.js:205-212`. `siteKey()` keeps only the last two labels of the host and does not use the Public Suffix List.
- **Effect:** `a.vercel.app`, `b.vercel.app` and `evil.vercel.app` (likewise netlify.app, github.io, pages.dev and herokuapp.com) all map to the same key. A JWT stored by customer A's app is sent as `Authorization: Bearer` to an attacker's app on the same platform (`proxy.controller.js:666-673`).
- **Fix:** key on the full hostname, or use `tldts`/`psl`.

#### S-03 · MEDIUM · The outbound-proxy fallback skips the SSRF guard (only when `OUTBOUND_PROXY` is set)
- **Where:** `proxy.controller.js:507-532`.
- **Problem:** `HttpsProxyAgent` has no `safeLookup` and no `beforeRedirect` check, and it follows 5 redirects. An attacker's site answers 403 to trigger the fallback, then redirects to `169.254.169.254` or an internal host.
- **Fix:** set `maxRedirects: 0` and re-check every hop with `isPublicUrl`.

#### S-04 · HIGH (deployment) · The working-copy compose turns production into dev mode with SSRF open
- **Where:** `docker-compose.yml:109,115` sets `NODE_ENV=development` and `PROXY_ALLOW_PRIVATE=true`. The uncommitted `docker-compose.override.yml` has every line commented out.
- **Effect:** if this working copy is deployed, the SSRF guard is off. The proxy can reach Mongo, Redis, cloud metadata and localhost, and CORS accepts `localhost:*`.
- **Fix:**
  - Do not commit or deploy this file.
  - Make the base compose file safe by default.
  - Refuse to start with `PROXY_ALLOW_PRIVATE=true` when `NODE_ENV=production`.

#### S-05 · LOW-MEDIUM · Other proxy hardening

| Issue | Where | Fix |
|---|---|---|
| Upstream TLS isn't verified, so staging logins typed through the proxy can be intercepted on the network path | `proxy.controller.js:50` (`rejectUnauthorized:false`) | Verify certificates; show an "insecure certificate" page when it fails. |
| One global relay token (about 25 h) is embedded in every page, guest pages included. It isn't bound to a URL, so the Cloudflare Worker is an open fetcher for anyone holding it | `utils/relayToken.js:142-159`, `cloudflare-relay/worker.js:66-73` | Sign the URL or host plus the project into the token. |
| `__markup_proxy_ctx` is `httpOnly:false`, and the upstream `Referrer-Policy` header is copied through, so the proxy token can leak to third parties | `proxy.controller.js:461`, `:424-428` | Make the cookie HttpOnly; skip `referrer-policy` when copying headers. |
| Revoking a share link reaches the guest proxy up to 60 s late; archived projects stay reviewable through their own link | `proxy.controller.js:170-181`, `utils/sharing.js:74-91` | Clear the cache on share changes; check archived status on both paths. |
| The SSRF blocklist is missing `2002::/16`, `100::/64` and `::ffff:0:0/96` | `utils/ssrfGuard.js` | Add them. |

**What held up:** I tested the SSRF guard on Node 22 against decimal, octal, hex and short IPv4 forms, IPv4-mapped IPv6, NAT64 and `fd00::/8`, and it blocked all of them. The IP is pinned at connect through `safeLookup`, which defeats DNS rebinding. Redirects are re-checked on every hop. Non-http schemes are refused.

### 1B. Authorization and data exposure inside a tenant

**Result: no cross-tenant access (IDOR) found.** Every lookup of a pin, comment, version, invitation, notification, integration or ticket by id is scoped to the caller's project or org. The problems are leaks **inside** an org, and boundaries a lower role can get around.

#### S-06 · HIGH · The project list leaks share-link secrets to view-only users and org guests
- **Where:**
  - `controllers/project.controller.js:210-218` returns `{...project.toObject()}`.
  - The secret-stripping transform is defined only for `toJSON` (`models/Project.js:96-107`), so `toObject()` skips it.
  - The client depends on the leak: `ShareProjectModal.js:32` reads `shareSettings.password`.
- **What leaks:** `shareSettings.token`, `passwordHash` and the legacy plaintext `password`.
- **Exploit:**
  1. An org guest with `view` access calls `GET /api/projects`.
  2. They read the share token and password (or crack the bcrypt hash offline).
  3. They call `/api/guest/<token>`, then post pins and comments as **any name or email**.

  This gets around the view-only level, the guest-role cap and author identity.
- **Fix:**
  - Use `toJSON()` or `sanitizeShareSettings` per item.
  - Return `shareSettings.token` only to people who manage the project, in both the list and the detail endpoint.
  - Finish the `hashSharePasswords` migration and drop the plaintext field.

#### S-07 · HIGH · Any org user, including guest-role clients, can read invoices and tax details
- **Where:** `routes/billing.routes.js:17-28` applies only `auth`.
  - `getPlan` (`billing.controller.js:28`)
  - `getInvoices` (`:276`)
  - `downloadInvoicePdf` (`:302`)
  - `getBillingDetails` (`:505`)
- **Effect:** an agency's client, invited as a guest, can download the agency's tax invoices and see its legal name, address, GSTIN/VAT, amounts and provider payment ids.
- **Fix:** add `authorize('owner','admin')` to these routes and hide the Billing tab for other roles (`SettingsPage.js:26`).

#### S-08 · MEDIUM · Support-role admins see superadmin-only billing data
- **Where:**
  - `GET /api/admin/organizations/:id` (`admin.routes.js:22`, no `requireAdminRole`) returns all invoices, `subscription.*Id`, `deal` and `billingDetails` (`admin.controller.js:419, 478-500`).
  - `GET /api/admin/stats` exposes unpaid totals and overdue invoices.
- **Fix:** strip these fields for `req.admin.role === 'support'`, or accept it as policy and write that down.

#### S-09 · LOW · An org admin can extract the masked Jira API token
- **Where:** `controllers/integration.controller.js:144-158, 223-230`.
- **Exploit:** an admin PATCHes `config.domain` to a host they control, sending back the masked token. The server keeps the stored token. "Test" then sends that token with Basic auth to their host.
- **Fix:**
  - Require a new token whenever `domain` or `email` changes.
  - Validate `projectKey`, which is currently put into the URL path as given.

#### S-10 · LOW · Other authorization gaps

| Issue | Where |
|---|---|
| A project or workspace manager can check whether any email has an account in another org ("Already belongs to another organization") | `project.controller.js:358-365`, `workspace.controller.js:287-291` |
| `updatePin` and `reorderPins` ignore the feedback deadline (423) and accept any status text up to 200 characters | `pin.controller.js:250-311, 469-499` |
| Guest name and email are not checked for type, length or format, so a guest can pose as a team member | `guest.controller.js:320-329, 419-425` |

### 1C. Authentication and sessions

**Result: no Critical or High issues.**

**What's solid:**
- JWTs are pinned to HS256, and the server refuses to boot with a weak secret.
- Admin sessions, 2FA challenges and customer sessions use separate keys.
- One session per user; logout, password change and reset rotate it and close sockets.
- Reset tokens are 32 random bytes, stored hashed, short-lived and single-use.
- Email OTP uses `crypto.randomInt`, is stored hashed and allows 5 attempts.
- TOTP has replay protection, and recovery codes are claimed atomically.
- Login runs a dummy bcrypt for unknown emails.
- The NoSQL sanitizer handles Express 5's `req.query` correctly.
- No cookie auth exists, so the CSRF exemptions are harmless.
- CORS uses a fixed allowlist.

#### S-11 · MEDIUM · A customer can lock an admin out of the 2FA step
- **Where:**
  - `middleware/rateLimiters.js:116-138`: `twoFactorLimiter` keys on the admin id read from the `challengeToken` **without checking its signature**.
  - Customers learn admin ids from their own activity feed. `getOrgActivity` (`auth.controller.js:889-929`) returns `adminActor` and `metadata.adminName` for admin-panel actions on their org.
- **Exploit:** five forged requests every 15 minutes, with no credentials, keep that admin unable to finish signing in.
- **Fix:**
  - Count failures only for challenges whose signature checks out.
  - Strip `adminActor` and `adminName` from the customer feed and from the GDPR export.

#### S-12 · LOW · Other authentication items

| Issue | Where | Fix |
|---|---|---|
| The session check is skipped when either `sessionToken` is null. Not exploitable today | `middleware/auth.js:40`, `server.js:79-85`, `proxyAuth.js:76` | Require both values and compare them strictly; reject tokens that carry a `purpose` claim. |
| The session JWT is accepted from `?token=` on every route (nothing uses it), so it can leak through logs and Referer | `middleware/auth.js:17-21` | Remove it. |
| Forgot-password waits for SMTP only when the account exists, which reveals existing accounts by timing | `auth.controller.js:614-640` | Send without waiting, as the admin version does. |
| Reset links stay valid after a password change | `auth.controller.js:528-530`, `adminAuth.controller.js:111` | Clear `resetPasswordToken` on change. |
| An email change doesn't notify the old address or rotate the session | `auth.controller.js:473-498` | Notify the old address and rotate the session. |
| Account deletion asks for no password | `auth.controller.js:552-604` | Require the password. |
| On a database with no customers (for example after the admin migration), the first signup skips the OTP check | `auth.controller.js:224-244` | Use an explicit bootstrap flag instead of the zero-user check. |
| Invitation tokens are stored in plaintext | `models/Invitation.js:43` | Store them hashed. |
| Proxy sub-resources ignore logout for up to 24 h | `proxyAuth.js:30-52` | Check the session on the fast path too (cached). |
| The 2FA key falls back to a value derived from `JWT_SECRET`; `AdminUser.role` defaults to `superadmin`; `requireAdminRole` fails open | `secretBox.js:7`, `AdminUser.js:14`, `adminAuth.js:48` | Set `TWO_FACTOR_KEY`; default the role to `support`. |
| Weak customer password policy; no customer 2FA; a 7-day JWT in localStorage with no CSP | `passwordPolicy.js`, `AuthContext.js` | Add a CSP on the app, shorter sessions, and optional 2FA. |

### 1D. Uploads and XSS

**Result: clean.** I found no way to execute script.

- **Uploads:** the stored extension comes from the mimetype, files get UUID names, and SVG and HTML are refused. `/uploads` sends `nosniff`, and anything that isn't an image or PDF is served `CSP: sandbox` and as a download. No path traversal: `storage.js:172-178` keeps paths under the uploads root. pdf.js 5.4 includes the CVE-2024-4367 fix.
- **Comments:** sanitize-html runs on the server (Quill allowlist; http, https and mailto only) and DOMPurify runs again on the client. Edit and guest paths are sanitized too.
- **Emails and integrations:** email templates escape every value through `esc()`; Slack, Discord, Teams and Jira payloads are escaped.
- **Low items:**
  - Avatar and logo uploads skip the storage quota, and replaced files are never deleted, so disk can be filled (`auth.routes.js:17,19`).
  - `websiteUrl` and `pageUrl` aren't checked for scheme and are rendered as `href` (`admin/src/pages/ProjectsPage.js:68`, `TechnicalDetails.js:161`). React 19 blocks `javascript:` today. Validate `http(s)` on the server anyway.
  - The parent window checks the message origin but not `event.source` (`useIframeMessages.js:47`), so a reviewed site can forge `MARKUP_*` messages such as a fake screenshot or page URL.

### Findings

#### RT-1 · HIGH · Pin `context` is pushed over the socket to org guests
- **Where:** the REST endpoint strips `context` for guests (`pin.controller.js:236`). The socket emits send the full document: `pin.controller.js:96-100, 313-319, 426-430` and `guest.controller.js:385`.
- **What leaks:** console errors, failed requests, selectors and environment details reach every guest-role user who has the project open.
- **Fix:** build the socket payload with a shared serializer that drops `context`.

#### RT-2 · HIGH · People who lose access keep receiving events
- **Where:** `join:project` checks access only when someone joins (`server.js:104-116`). Nobody is removed from the room on `removeMember`, `updateMemberAccess`, `setWorkspaceMembers`, workspace delete or move, or an org role demotion.
- **Effect:** a removed member's open tab keeps receiving every pin and comment, with bodies and author emails.
- **Fix:** run `io.in('user:<id>').socketsLeave('project:<pid>')` after each access change. For workspace and role changes, re-check the rooms or disconnect the user's sockets.

#### RT-3 · HIGH · A deleted account keeps its live sockets
- **Where:** `deleteAccount` (`auth.controller.js:552-604`) never calls `endUserSockets`.
- **Fix:** call `endUserSockets` before responding.

## Phase 3: Billing, payments and business logic

**What's solid:**
- Razorpay webhooks use HMAC over the raw body with `timingSafeEqual`.
- PayPal webhooks are verified through PayPal's API.
- `settleInvoice` claims invoices atomically, so replays and webhook/verify races are safe.
- The client sends only a plan id; prices are computed on the server.
- Invoice numbers come from an atomic `$inc`.
- Dates are handled in UTC.
- The org purge cascade is complete.

#### B-1 · HIGH · Scheduling, then cancelling, org deletion clears payment-overdue and admin locks
- **Where:** `auth.controller.js:1028-1031` overwrites `lockedReason` whatever the current lock is. `:1054-1059` then unlocks.
- **Exploit:** a locked, overdue org (or one an admin locked for abuse) calls delete, then cancel-deletion, and is fully usable again. It can repeat this every month instead of paying.
- **Side effect:** cancelling deletion also resets `cancelAtPeriodEnd = false`, silently undoing a cancellation the customer chose earlier.
- **Fix:** keep the deletion state separate from `isLocked`, or save the previous lock and restore it on cancel.

#### B-2 · HIGH · An overdue org gets the unpaid month free plus a new month
- **Where:** `runBilling.js:192-194` advances the period when it issues the renewal. A locked org can then check out its own plan (`billing.controller.js:133`). `settleInvoice.js:85-93` extends from the already-advanced end, and `:141-146` voids the unpaid renewal.
- **Effect:** one payment covers two periods.
- **Fix:** when a checkout finds a pending renewal, settle that renewal with it, or roll the period back first.

#### Medium

| ID | Issue | Where | Fix |
|---|---|---|---|
| B-3 | PayPal settles when the **order** says COMPLETED, without checking the capture status, amount or currency. If a pending capture is later denied, the denial is ignored because the invoice is already paid | `payments/paypalProvider.js:137-149, 267` | Require `captures[0].status==='COMPLETED'` and matching amount and currency; handle DENIED/REVERSED on paid invoices. |
| B-4 | A custom deal price applies to **any** plan, so a Starter deal buys Pro at the Starter price | `razorpayProvider.js:60-66`, `paypalProvider.js:83-89` | Add `deal.plan`. |
| B-5 | Renewals can stop for good: if a paid invoice already exists for that `YYYY-MM`, the org is skipped every day and never moved forward | `runBilling.js:141-145` | Key renewals on the exact period start. |
| B-6 | Locks are matched by display text, so an admin lock typed as "Payment overdue" can be paid off | `orgUtils.js:11-16` | Store a lock type separate from the reason. |
| B-7 | Removing someone from an org gives them a fresh 30-day Pro trial; repeated invite and removal mints trials | `workspace.controller.js:418-426` | Give them a free org, or track `trialUsedAt`. |

- Invitation tokens are stored as hashes.
- Deleting your account requires the password, and only removes invitations from your own org.
- Replaced avatars and logos are deleted.
